# 基线数据

> 本文档记录 Ascend NPU / CANN 8.5.0 各算子和模型的基准性能与精度数据，作为度量报告中对比的参照标准。

## 说明

- 所有基线数据在**单卡 Ascend NPU，CANN 8.5.0**环境下测量
- 性能数据取 **100 次迭代的均值**，前 10 次为预热迭代
- 精度基准以 **FP32 CPU 计算结果**为参考值

## errMsg 质量达标标准

### 综合质量分等级

| 质量等级 | 综合质量分 | 含义 | 处理建议 |
|---------|---------|------|---------|
| **EXCELLENT** | ≥ 90 | errMsg 信息完整，可直接定位根因 | 无需改善，记录为优质日志样本 |
| **GOOD** | 70 ~ 89 | 可定位至模块，需结合参考文档分析 | P3 持续改进 |
| **FAIR** | 50 ~ 69 | 只能确定问题类型，需补充收集日志 | P2 优化日志收集条件 |
| **POOR** | < 50 | 无法从 errMsg 直接定位，必须重跑 | P1 立即改善日志条件并重新评估 |

### 各维度达标阈值

| 维度 | 指标 | 达标值 | EXCELLENT | GOOD | FAIR | POOR |
|------|------|--------|-----------|------|------|------|
| **识别完整性** | 首报错码已提取 | true | true | true | true | false |
| | 错误级联深度 | ≤ 3 | ≤ 2 | ≤ 3 | ≤ 5 | > 5 |
| **文档符合度** | 文档记录率 | ≥ 80% | ≥ 95% | ≥ 80% | ≥ 60% | < 60% |
| | 未记录错误码数量 | 0（或仅 E\*9\*\*\*） | 0 | ≤ 1 | ≤ 3 | > 3 |
| | 描述与文档一致 | true | true | true | N/A | false |
| **格式规范度** | 错误码格式合规率 | 100% | 100% | 100% | ≥ 90% | < 90% |
| | 含 Ascend Error Message 块 | true | true | true | N/A | false |
| | 日志行格式合规率 | ≥ 90% | ≥ 95% | ≥ 90% | ≥ 75% | < 75% |
| | 含文件名+行号信息率 | ≥ 80% | ≥ 90% | ≥ 80% | ≥ 60% | < 60% |
| **问题指导性** | 能确定问题模块 | true | true | true | true | false |
| | AI Core Error 含 fault_kernel_name | true | true | true | false | false |
| | 含定位三要素（device/stream/task） | true | true | true | false | false |

| | 指导性评分 | ≥ 70 | ≥ 85 | ≥ 70 | ≥ 50 | < 50 |

### 按场景的 minimum 要求

| 场景 | 必须满足的最低要求 |
|------|----------------|
| AI Core Error（EZ9999）| 首报错码已提取 + `Ascend Error Message` 块完整 + `fault_kernel_name` 存在 + `device_id/stream_id/task_id` 三要素 |
| OOM（EL0004 / HBM OOM）| 首报错码已提取 + 错误描述含内存相关关键词（memory/OOM/allocation）|
| HCCL 超时（EI0002）| 首报错码已提取 + 包含超时等待时长（wait_time 或 timeout 字段）|
| 进程中断 / coredump | 首报错码已提取 + 含 C++ Call Stack 或 Python Traceback |
| 进程卡住 | 无错误码时须有最后一条 INFO 日志的时间戳 + 卡住阶段描述 |

## 诊断可信度达标标准

> 由评估 Skill 的 `assess_confidence.py` 给出，评分规范见 eval-skill 的
> `references/confidence-assessment.md`。errMsg 质量衡量的是**日志本身**好不好用，
> 诊断可信度衡量的是**结论**站不站得住，两者独立。

### 可信度等级

| 等级 | 分数 | 报告中的结论强度 | 案例库沉淀 |
|------|------|---------------|-----------|
| **HIGH** | ≥ 85 | 可作定论 | 关键项满足且修复已验证 → 写入 `cases.md` |
| **MEDIUM** | 70 ~ 84 | "当前证据下最可能的原因" | 进候选区 `cases-pending.md` |
| **LOW** | 50 ~ 69 | 必须写作"初步判断" | 不入库 |
| **INSUFFICIENT** | < 50 | 不给根因结论，只给排查方向 | 不入库，回到采集补证 |

### 各维度达标阈值

| 维度 | 满分 | 达标值 | 说明 |
|------|------|--------|------|
| D1 证据完整性 | 25 | ≥ 20 | 首报错原文（8 分）是入库关键项，缺失即不得入库 |
| D2 证据一致性 | 20 | ≥ 14 | 至少 2 个独立来源互证 |
| D3 因果链闭合性 | 25 | ≥ 20 | 链路无跳跃（9 分）为必得项 |
| D4 复现与验证 | 15 | ≥ 9 | 入主库要求 `fix_verified` 为 true |
| D5 知识对齐 | 15 | ≥ 10 | 错误码有文档 + 匹配案例或源码证实 |

### 入库关键项

| 关键项 | 达标值 | 未满足的后果 |
|------|--------|------------|
| 首报错日志行已定位 | true | 不得入库；结论方向可能整体偏移 |
| 因果链无跳跃 | true | 不得入库；结论含未证实的关键假设 |

分数由五维加分决定，不做额外压分。这两项本身是权重最高的检查项（8 分、9 分），
缺失时总分自然落到低区间；它们额外承担「阻止案例入库」这一作用。

### 按场景的 minimum 要求

| 场景 | 达到 HIGH 的必要条件 |
|------|-------------------|
| AI Core Error（EZ9999）| 首报错原文含 `fault_kernel_name` + device/stream/task 三要素 + msaicerr 分析结论 + 子类型已判定 |
| OOM（EL0004 / HBM OOM）| 内存占用来源已量化（参数/激活/通信 buffer）+ `npu-smi` 或 profiling 佐证 |
| HCCL 超时（EI0002）| 各 rank 状态已比对 + 已定位首个异常 rank + 排除网络/慢节点假设 |
| 进程中断 / coredump | core 与 exe 匹配 + 符号完整 + 崩溃帧映射到源码 `file:line` + 版本已确认 |
| 进程卡住 | 实时堆栈已导出 + 卡住阶段已定位 + 已排除 fork 死锁/HCCL 超时等竞争假设 |
| 性能劣化 | profiling 数据 + 基线对比 + 瓶颈类型已定位（计算/带宽/调度）|
